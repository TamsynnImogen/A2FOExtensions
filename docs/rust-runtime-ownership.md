# Rust runtime ownership status

This tracker covers authoritative persistent ownership across all 48 built-in feature families, shared core state, and renderer state. It is not complete. The earlier 151 portable controller units are unchanged and earn no ownership credit here.

The subsequent [native platform and renderer phase](rust-native-platform-renderer.md) now has bounded Rust compressed-texture view ownership. This document and its feature counts describe the stage-eleven ownership checkpoint; the broader rewrite remains incomplete.

The machine-readable stage-eleven status is [ownership-status-v2.json](../build/rust-migration-stage11/runtime-ownership/ownership-status-v2.json). [Version 1](../build/rust-migration-stage11/runtime-ownership/ownership-status-v1.json) is preserved. The adjacent [ownership-inventory.json](../build/rust-migration-stage11/runtime-ownership/ownership-inventory.json) is an initial historical heuristic snapshot only: its file hashes and declaration-shaped source lines describe bytes at inventory-generation time, and its 1,434 candidate incidences are not declaration counts, ownership counts, or progress measures. Current feature status and source evidence are kept separately; do not refresh or interpret the heuristic snapshot as a completion ledger.

## Remaining scope and acceptance

Two feature families (StationRotation and NormalWeaponTech) have bounded Rust ownership evidence; the other 46 remain unaudited/incomplete. Core ownership is partial: native policy maps, caches, root strings, and platform resources remain to audit. Renderer ownership was pending in full at this checkpoint; the subsequent native phase now has a bounded compressed-texture view owner, with broader renderer ownership still incomplete. No percentage-complete claim is supported.

For each feature and shared group, review all persistent state: scalar flags, containers, handles/resources, worker state, and process-lifetime objects. Establish the authoritative data owner, lifetime, cleanup behavior, ordering, locking, reentry, callback mutation, and failure behavior with focused evidence. Moving policy behind a Rust call while C++ retains authoritative storage does not qualify. Verify each applicable built-in and standalone load path, then separate source review, production whole-DLL build, native headless fixtures, staged/deployed proof, and in-game acceptance.

The shutdown-clear skipped-handle hazard has been addressed by consuming the private retiring generation and continuing cleanup after native logging/formatting failures; the first native exception is rethrown after cleanup. A live global-handler iteration hazard remains: clearing or replacing the registry during callback dispatch can stop further dispatch. Explicit unload assumes workers and dispatch are quiescent; the process-lifetime default remains unchanged, and unload is not added under loader lock. NormalWeaponTech's former global native `exception_ptr` is now a stack-owned `NormalInitContext`. Do not claim all lifetimes are resolved. Keep native engine ABI objects/layouts and COM calls behind explicit adapters unless separately proven; the foreign MSVC6 `vector<char*>` boundary in `core/dllmain.cpp` must not be reinterpreted as Rust-owned storage.

The old inventory's examples (including gameplay maps, UI state, workers, and renderer D3D resources) are audit leads only. Its heuristic can miss authoritative state or match non-authoritative declarations. Use the current status JSON for scope/status and record newly reviewed source evidence there without retroactively changing the historical inventory.
