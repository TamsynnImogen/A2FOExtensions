# A2FOAlwaysShowShields

  alwaysShowShields = 1

  ### Behaviour

  - Missing or zero: disabled.
  - Any non-zero integer: enabled.
  - Textual true values: true, yes, on.
  - Textual false values: false, no, off.
  - Command names are case-insensitive.
  - Normal ODF #include inheritance is supported.
  - A local value overrides inherited values.
  - It applies to ships and stations.
  - The effect disappears at zero shields and returns when shields become positive.

  There are no additional controls for:

  - shield colour
  - shield effect type
  - effect duration
  - scan interval
  - shield geometry
  - activation threshold

  Those are currently hardcoded. It uses Armada effect type 7, associated with the WEclairlink1 outline, with native
  effect colour 0.

  ### Files inspected

  The DLL does not parse any:

  - INI files
  - CFG files
  - SPR files
  - ART_CFG.h
  - RTS_CFG.h
  - localization headers

  It only reads ODF files, including a loose-ODF fallback that recursively indexes each extension root’s odf
  directory.

  ### Small inconsistency found

  The normal ParameterDB path accepts malformed values such as:

  alwaysShowShields = "1something"

  as enabled because it does not validate the complete numeric string. The loose-ODF fallback rejects that value.
  Proper values such as 0, 1, true, or false behave consistently.

# A2FOAnimatedHardpoints.dll

Its only modder-facing contract is an existing SOD convention:

  1. Create a type-0 null/hardpoint node.
  2. Add an ordinary SOD matrix-animation channel.
  3. Give the channel the same identifier as that node, or animate one of its ancestors.

  Example conceptually:

  Node: hp01
  Matrix animation channel: hp01

  The identifier comparison is case-insensitive.

  ### Behaviour and limits

  - Only type-0 null nodes are redirected.
  - Mesh, sprite and emitter nodes retain native behaviour.
  - Animated ancestor transforms are inherited by descendant hardpoints.
  - Gameplay calls to both world position and world transform use the animated result.
  - Animation is evaluated separately for each model instance.
  - Triggered animations use that instance’s current animation time.
  - An untriggered animation uses its first frame.
  - Up to 4,096 matrix channels are inspected per model.
  - Node ancestry traversal is limited to 256 levels.
  - Identifiers are limited to 255 characters.
  - Duplicate node names should be avoided because native recursive lookup may select the first matching visible
    node.

  There are no modder controls for:

  - animation speed
  - animation selection
  - channel enable/disable
  - hardpoint prefixes
  - interpolation
  - cache size
  - supported node types

  Those remain part of the existing SOD animation data or are hardcoded implementation details.

# A2FOBuildTooltips.dll

  ### Native object input

  It displays the object’s existing native build time—normally authored with stock Armada’s:

  buildTime = 42.0

  The DLL reads the resolved class value and Armada’s local-team adjusted result. It also accounts for the Instant
  Action build-time multiplier.

  The displayed time:

  - is rounded to the nearest whole second;
  - may display 0;
  - appears only for actual build-item buttons;
  - uses game seconds, not real-world seconds.

  ### Localization keys

  It directly queries these existing Dynamic_Localized_Strings.h keys:

   Key                       Fallback
  ━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━
   GUI_CP_AMOUNT_SEPARATE    /
  ────────────────────────  ──────────
   GUI_CP_END_EXTRA          )

  Normal output resembles:

  /42 [0x8A glyph])

  Verbose output uses hardcoded English:

  /42 seconds)

  second and seconds are not localization keys, so their wording currently cannot be changed through the string
  table.

  ### Font/SPR convention

  Compact build-time text emits byte 0x8A.

  Every font used by build tooltips therefore needs:

  - a 0x8A UV frame in its Font*.spr animation;
  - a matching width frame;
  - corresponding artwork in the font texture.

  The DLL does not parse SPR files itself—it simply emits the byte and relies on Armada’s font configuration.

  ### Commands consumed through A2FOResources.dll

  creditsCost
  collectiveconnectionsCost

  supplyIcon
  creditsIcon
  collectiveconnectionsIcon

  Verbose tooltips use:

  tritaniumRes
  supplyRes
  creditsRes
  collectiveconnectionsRes

  These commands belong to A2FOResources.dll; BuildTooltips obtains their resolved values through its exported API.

  ### No other configuration

  It does not parse:

  - INI files
  - CFG files
  - ordinary SPR commands
  - ART_CFG.h
  - RTS_CFG.h
  - custom tooltip ODF fields

# A2FOCheats.dll

  ### RTS_CFG.h

  Recognised field names are case-sensitive:

  SHOWMETHEMONEY_DILITHIUM
  SHOWMETHEMONEY_TRITANIUM
  SHOWMETHEMONEY_METAL
  SHOWMETHEMONEY_SUPPLIES
  SHOWMETHEMONEY_CREW

  Typical configuration:

  float SHOWMETHEMONEY_DILITHIUM = 10000;
  float SHOWMETHEMONEY_TRITANIUM = 10000;
  float SHOWMETHEMONEY_METAL = 10000;
  float SHOWMETHEMONEY_SUPPLIES = 10000;
  float SHOWMETHEMONEY_CREW = 10000;

  Rules:

  - Each defaults to 10000.
  - Valid range is 0 through 100000000.
  - Zero disables that particular grant.
  - Integer, decimal and scientific literals are accepted.
  - An optional f or F suffix is accepted.
  - Expressions and macros are not evaluated.
  - // and /* ... */ comments are handled.
  - Later declarations in the same file win.
  - Values inherit individually through Data → parent mods → active mod.
  - Invalid higher-precedence values retain the inherited value.

  Important correction: the central reference calls these “integer declarations”, but the DLL uses strtof and
  accepts floating-point values. The declaration’s written type is effectively ignored by its text parser.

  These names refer to Fleet Operations’ historical resource helper slots. In particular, TRITANIUM and SUPPLIES do
  not grant the new independent A2FOResources Tritanium and Supply pools. There are no corresponding configurable
  grants for A2FO Credits or Collective Connections.

  ### Runtime cheat commands

   Command           Behaviour
  ━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   showmethemoney    Grants all five configured resource amounts
  ────────────────  ────────────────────────────────────────────────────────────────────
   m                 Moves every selected craft 200 world units forward
  ────────────────  ────────────────────────────────────────────────────────────────────
   dis               Disables shields on every selected craft for 10,000 seconds
  ────────────────  ────────────────────────────────────────────────────────────────────
   elim              Eliminates the team belonging to the first suitable selected craft
  ────────────────  ────────────────────────────────────────────────────────────────────
   crash             Intentionally terminates Fleet Operations

  showmethemoney is an existing Fleet Operations command whose handler is replaced. The other four are restored or
  corrected by this module.

  expl is not modified; it continues destroying only the selected object.

  All these commands are registered as unavailable in multiplayer, leaving Fleet Operations’ multiplayer cheat gate

  There are no configurable settings for:

  - m movement distance
  - dis duration
  - the elim selection rule
  - enabling cheats in multiplayer
  - adding Credits or Collective Connections

# A2FODirectionalShields.dll

  ### Direct Craft ODF commands

  directionalShields = 1
  forwardShieldStrength = 200
  aftShieldStrength = 150
  portShieldStrength = 150
  starboardShieldStrength = 150
  maxShields = 650 // Native field consumed for validation

  Rules:

  - Field names are case-insensitive and use normal inherited ODF values.
  - directionalShields is the mandatory activation gate.
  - Accepted true values include any positive number, true, yes, or on.
  - 0, false, no, and off disable it.
  - enabled is not accepted.
  - All four strengths must be finite and greater than zero.
  - Floats, scientific notation and an optional f suffix are accepted.
  - If resolved/inherited maxShields exists, it must be positive and match the facing total.
  - Matching tolerance is 0.01 or 0.01% of the larger value, whichever is greater.
  - If maxShields is entirely absent, the DLL installs the facing total as the native maximum.

  Native maxHealth, healthRate, and shieldRate are not parsed by this DLL. Hull remains separate, while native
  shield recharge changes the aggregate and is then distributed across depleted facings.

  ### No direct UI or file configuration

  This DLL contains no direct:

  - GUI CFG commands
  - ART_CFG.h or RTS_CFG.h parser
  - INI settings
  - localization keys
  - sprite or texture names
  - weapon ODF commands
  - save-format fields

  The following documented controls actually belong to A2FOCraftIdentity.dll:

  - forwardShieldPos, aftShieldPos, portShieldPos, starboardShieldPos
  - All infoSingleDirectionalShields* rectangles
  - directionalShieldColor, directionalShieldLowColor, directionalShieldCriticalColor
  - All five directionalShield*Position/DisplayMode ART fields
  - dsf, dsb, dsl, dsr and their textures

  ### Dependencies

  - A2FOWeaponDamageControls.dll is required for gameplay because it owns the shared Craft::Damage hook.
  - Module ordering in activeX does not matter; they perform a late handshake.
  - A2FOCraftIdentity.dll is optional and only provides the selected-panel display.
  - A2FOAlwaysShowShields.dll remains independent.

  ### Gameplay and persistence

  - Hits use the attacker’s target-local horizontal direction.
  - Exact diagonal boundaries select forward or aft.
  - An empty facing exposes the hull even if other facings remain charged.
  - Damage without a resolvable weapon owner remains aggregate damage and is later spread proportionally.
  - Native recharge is shared evenly among depleted facings.
  - Per-facing values are not saved. Loading redistributes the saved aggregate percentage proportionally.

  ### Findings

  Documentation is generally accurate, with two omissions:

  - It presents directionalShields = 1 as the only activation syntax, while the parser accepts positive numbers and
    true/yes/on.

  - The maxShields comparison tolerance is undocumented.

  There is also a very minor validation edge case: four individually finite but enormous strengths can overflow
  their summed total. With an explicit enormous maxShields, the infinity comparison could incorrectly accept the
  policy. Normal gameplay-sized values are unaffected.

# A2FOEnergySystems.dll

  ### Craft ODF commands

  Photon store:

  maxPhotonTorpedoes = 80
  photonTorpedoRate = 1.0
  photonTorpedoRechargeMode = 1

  Quantum store:

  maxQuantumTorpedoes = 20
  quantumTorpedoRate = 0.25
  quantumTorpedoRechargeMode = 2

  Resupply providers:

  torpedoResupply = 1
  torpedoResupplyRange = 300

  It also consumes native classLabel:

  - shipyard automatically provides resupply.
  - RepairShip automatically provides resupply.
  - Matching is case-insensitive.
  - torpedoResupply explicitly overrides the automatic result.

  Rules:

  - Fields are case-insensitive and include inherited ODF values.
  - Capacities, rates and ranges accept finite non-negative floats, scientific notation and optional f.
  - Missing, zero or invalid capacity disables that store.
  - Missing or invalid rate becomes zero.
  - Recharge mode must be the exact integer 0, 1, or 2.
  - Missing or invalid recharge mode silently defaults to 1—automatic recharge.
  - New stores start full.
  - torpedoResupplyRange defaults to 200.
  - A zero range is accepted; negative or invalid values retain 200.
  - The range belongs to the provider, not the receiving Craft.
  - Mode 2 requires the same team and uses three-dimensional distance.
  - A provider may resupply itself.

  torpedoResupply accepts:

  - True: positive numbers, true, yes, on
  - False: 0, false, no, off
  - enabled is not accepted

  ### Weapon ODF commands

  Put exactly one on the general weapon ODF:

  photonTorpedoCost = 1

  or:

  quantumTorpedoCost = 1

  Both costs accept positive fractional values. A configured weapon:

  - Checks the owner’s matching store before every projectile.
  - Cannot fire if its owner lacks that store.
  - Pays after each successfully launched projectile.
  - Can stop partway through a multi-projectile volley.
  - Is ignored and behaves natively if both costs are positive.
  - Behaves natively if neither cost is positive.

  The fields belong on the weapon ODF, not its ordnance ODF.

  ### Recharge behaviour

  - Mode 0: no recharge.
  - Mode 1: automatic recharge.
  - Mode 2: recharge only within the provider’s range.
  - Recharge remains fractional internally.
  - Amounts are clamped to 0..maximum.
  - photonTorpedoRate and quantumTorpedoRate are units restored per game second.

  ### UI ownership

  The current binary contains no live GUI, localization, sprite or presentation commands.

  All these belong to A2FOCraftIdentity.dll:

  - photonTorpedoDisplayMode and quantumTorpedoDisplayMode
  - All *ValueDisplayMode, *Label, *Tooltip, *VerboseTooltip, *Icon, and *IconPos fields
  - All Photon/Quantum GUI rectangles and colours
  - GUI_SD_SPE_READY, GUI_SD_AMMO_WAITING
  - large_shield_bar and atlas sprite handling

  EnergySystems contains an old direct UI implementation in its source, but kSelectedInfoUiEnabled is hardcoded
  false; the compiler has removed its GUI field strings from the current DLL. CraftIdentity instead reads
  EnergySystems’ exported live values.

  There are no direct INI, CFG, ART/RTS header, SPR, texture or localization parsers.

  ### Save data

  Configured Craft append a 16-byte versioned block labelled a2fo_torpedoStores containing:

  - Magic
  - Version 1
  - Current Photon amount
  - Current Quantum amount

  Loaded values are clamped to the current ODF capacities. Older saves lack this block and are intentionally
  rejected for configured Craft, so a new game is required after enabling the feature.

  If the save/load signatures are unavailable, gameplay still runs but persistence is disabled and logged.

  ### Native developer API

  The DLL exports getters for current, maximum and remaining reload time, plus Set and Add functions for both
  stores. These use float amounts and are not ODF commands.

  ### Documentation findings

  - Recharge mode’s default of 1 is not stated clearly.
  - Fractional weapon costs and the full torpedoResupply boolean syntax are undocumented.
  - The README says stores initially display whole current/maximum, but CraftIdentity’s actual default value mode is
    percentage.

  - docs/addresses.md still says EnergySystems registers its selected-info handler; that path is disabled.
    CraftIdentity pulls the exported values instead.

  - Presentation commands are included in the EnergySystems guide but should be labelled explicitly as
    CraftIdentity-owned.



# A2FOFeaturePack.dll

  ### Direct commands

  1. RTS_CFG.h

  int upgradePodMaximumTier = 6;

  - Default: 6
  - Valid: 3..16
  - Name is case-sensitive.
  - Value must be a plain positive decimal integer—no floats, signs, hex, macros, or expressions.
  - C/C++ comments and optional declaration prefixes are accepted.
  - The last assignment in that file determines whether the file’s setting is valid. A trailing invalid assignment
    discards earlier valid assignments from that file and retains the inherited setting.

  - Child RTS_CFG.h files replace the complete parent file, so modders must copy the full parent configuration.

  2. Upgrade-station ODFs

  tier0BuildItem0 = "pod_weapons_2"
  tier1BuildItem0 = "pod_weapons_3"
  tier2BuildItem0 = "pod_weapons_4"

  - tierTBuildItemX maps to upgradeLevel = T + 2.
  - T is 0..maximumTier-2; with the default maximum that is 0..4, and the absolute maximum is 0..14.
  - X is:
      - 0..56 for tier0BuildItemX
      - 0..57 for tier1BuildItemX and higher

  - Sparse indices are supported.
  - Missing commands preserve the existing entry.
  - An explicitly empty value clears that index.
  - Paths and an optional .odf suffix are accepted and reduced to the ODF basename.
  - The target must resolve to an upgrade ResearchPod with exactly the corresponding upgradeLevel.
  - Invalid entries are ignored and logged.
  - Each upgrade chain should retain the same X and upgradeSystem at every tier.

  upgradeLevel, upgradeSystem, the upgrade multiplier, podHardpoints, and the ResearchPod upgrade flag are existing
  native data consumed after Fleet Operations parses them; they are not new FeaturePack commands.

  3. BuildYard configuration ODFs

  module0RequiredTechnology = "fed_module_basic_tech.odf"
  module0PseudoTechnology = "fed_module_chassis_gate.odf"

  - X is the same zero-based index as native moduleXRequiredTechnology.
  - The implementation accepts indices through 1023, although actual usable indices remain constrained by Fleet
    Operations’ module configuration.

  - The value is resolved as a normal project ID.
  - If no native requirement exists, the pseudo project becomes the module’s only technology gate.
  - If both are different and valid, both must be available.
  - Missing, unresolved, empty, or project-ID-zero pseudo entries are ignored.
  - The fake project must be added to the selected .tt technology tree.
  - Native moduleConf and moduleXRequiredTechnology are not owned by FeaturePack.

  ### Automatic file conventions

  FeaturePack also provides recursive ODF discovery without additional commands:

  - Loose ODFs are discovered recursively beneath each extension root’s odf directory.
  - Registered overlays such as A1Compat’s Addon directory are also scanned.
  - Recursion is limited to 64 levels and reparse-point directories are skipped.
  - The archive name is specifically odf.fpq at each extension root.
  - FPQ versions 1 and 2 are accepted.
  - Only .odf files beneath an odf folder inside the archive contribute directories.
  - Lookups are basename-based and case-insensitive. Two nested files with the same basename cannot be addressed
    independently; precedence selects one winner.

  - Precedence is active mod over parent over Data, then override overlays, primary root, and loose before packed.
  - Fleet Operations’ total virtual-directory limit is 255.

  ### Not configurable

  These have no ODF/INI/CFG commands:

  - Ctrl-click ten-slot queue fill
  - Ctrl+Alt-click continuous production
  - Queue retry timing, markers, and save/load data
  - Hotkeys
  - Bink movie viewport scaling
  - HybridBuild callback bridge
  - Producer event dispatch
  - A1 Addon precedence registration

  FeaturePack directly parses no info.ini, ART_CFG.h, GUI CFG, SPR, localization, texture, or SOD settings.

  ### Documentation finding

  The central reference currently says all tierTBuildItemX indices are 0..56. The binary actually supports index 57
  for tier 1 and higher; only tier 0 stops at 56. The strict RTS_CFG.h syntax, BuildYard index ceiling, recursive
  depth/directory limits, and basename-collision rule are also undocumented.

  The compiled DLL contains the expected command strings and is newer than all its source files. The upgrade parser,
  FPQ paths, recursive ODF paths, documentation tests, and full Wine module-initialization smoke test all passed. No
  files were changed.

# A2FOFireArcs.dll

  ### Weapon ODF commands

  Place these in the general weapon ODF, not the ordnance ODF:

   Command              Behaviour
  ━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   fireArcMode          box or cone; case-insensitive
  ───────────────────  ───────────────────────────────────────────────────
   fireArcYaw           Horizontal centre; default 0, wraps to -180..180
  ───────────────────  ───────────────────────────────────────────────────
   fireArcPitch         Vertical centre; default 0, clamps to -90..90
  ───────────────────  ───────────────────────────────────────────────────
   fireArcYawAngle      Box total yaw width; default 360, clamps 0..360
  ───────────────────  ───────────────────────────────────────────────────
   fireArcPitchAngle    Box total pitch width; default 180, clamps 0..180
  ───────────────────  ───────────────────────────────────────────────────
   fireArcAngle         Cone’s total circular diameter; clamps 0..360
  ───────────────────  ───────────────────────────────────────────────────
   fireArcCenter        Compatibility alias for fireArcYaw
  ───────────────────  ───────────────────────────────────────────────────
   fireArcWidth         Compatibility alias for fireArcYawAngle

  Rules:

  - All widths are totals: 90 means 45 degrees on each side.
  - Boundaries are inclusive.
  - fireArcYaw overrides fireArcCenter.
  - fireArcYawAngle overrides fireArcWidth.
  - Supplying fireArcAngle without a mode selects cone mode.
  - Explicit cone mode requires fireArcAngle.
  - Box mode requires at least one of fireArcWidth, fireArcYawAngle, or fireArcPitchAngle.
  - Centre fields alone do not activate a valid custom arc.
  - Finite integer, decimal, scientific, quoted numeric and optional f suffix values are supported.
  - Widths outside their range are clamped, not rejected.
  - A malformed declared numeric field rejects the entire custom policy—even if that field would otherwise be unused
    by the selected mode.

  - An invalid or incomplete policy is logged and retains native Fleet Operations firing behaviour.
  - Weapons containing none of these fields remain completely native.

  Custom arcs replace only native restrictFireArc/fireArc directional checking. Range, target validity, obstruction
  and other native checks remain active.

  ### RTS_CFG.h

  int firearc = 1;

  - Default: enabled.
  - 1: enables custom arc enforcement and hover previews.
  - 0: disables the complete DLL’s runtime behaviour.
  - The identifier is case-sensitive.
  - Only literal 0 or 1 is accepted—no true, signs, floats, macros, or expressions.
  - Optional declaration prefixes and C/C++ comments are accepted.
  - Later valid extension roots override earlier roots.
  - Within one file, the final assignment controls validity. A trailing invalid assignment causes that file to be
    ignored and retains the inherited value.

  - Files over 2 MiB are ignored.

  As with upgradePodMaximumTier, a child RTS_CFG.h replaces the complete native parent file. The FireArcs README
  does not currently warn modders to copy the full parent configuration.

  ### Interface CFG colours

  fireArcBoundaryColor    = 0.10 0.90 1.00
  fireArcCenterColor      = 1.00 0.82 0.12
  fireArcValidTargetColor = 0.15 1.00 0.20

  Defaults:

  - Boundary: cyan, 0.10 0.90 1.00
  - Centre: gold, 1.00 0.82 0.12
  - Target inside arc: green, 0.15 1.00 0.20

  Each channel is clamped independently to 0..1. Missing, malformed or non-finite colours retain their default.
  These belong in the active interface GUI CFG, not ART_CFG.h.

  ### Existing native fields observed

  These are not new FireArcs commands:

  - restrictFireArc and fireArc: native directional policy retained when no valid custom arc exists.
  - weaponXiconpos: exposes the weapon icon needed to activate the hover preview.
  - Weapon range: sizes the preview to 35% of range, clamped to 80..500; invalid range uses 120.
  - wpnName, then ordName: used only to identify malformed policies in the log.
  - The weapon’s native hardpoint list: preview origin; up to 64 nodes are inspected before falling back to the
    owner’s centre.

  No special SOD hardpoint names are required.

  ### No other modder configuration

  The DLL has no direct:

  - INI settings
  - ART_CFG.h fields
  - SPR definitions
  - localization keys
  - texture or SOD names
  - technology-tree commands
  - save-format fields

  Its exported A2FOFireArcs_AllowWeaponTrigger function is a native module API, not a mod command.

  researchItem0  = "fed_research"

  1. evolveItemX currently becomes active only when there is also a valid yardItemX list. An evolve-only or

# A2FOInfoIni.dll

  [mod]
  DefaultGameSpeed = 5
  SettingsDirectory = My Mod

  ### DefaultGameSpeed

  - Accepts decimal integers 1..6.
  - Quoted values are accepted.
  - +3 and 03 are also accepted as decimal.
  - Floats, suffixes, trailing comments, zero and values above six are rejected.
  - It applies only as a first-run/default value.
  - An existing completed profile’s saved game speed takes precedence.
  - When an active mod is selected, Data and parent-mod speed values are not inherited.

  ### SettingsDirectory

  Supported forms:

  SettingsDirectory = Shared Mod
  SettingsDirectory = profiles\Classic
  SettingsDirectory = D:\Portable\Fleet Ops
  SettingsDirectory = \\server\share\Fleet Ops
  SettingsDirectory = Z:\Linux\Path
  SettingsDirectory = %APPDATA%\My Fleet Ops

  Resolution:

  - Bare name → standard mods\<name> settings folder.
  - Relative path with separators → relative to Star Trek Armada II Fleet Ops Config.
  - Drive and UNC paths → used directly.
  - Environment variables are expanded.
  - Forward slashes become backslashes.
  - A trailing backslash is added automatically.
  - Do not include Settings.xml; name its containing directory.
  - Active-mod values are not inherited from parent mods.
  - A Data-level SettingsDirectory acts only as the shared root for an active mod’s bare name.

  A bare Data shared root creates nesting such as:

  ...\mods\Shared Root\mods\Active Name\

  An absolute or separator-containing Data path is clearer for shared-root usage.

  ### Parser caveats

  - Section and key names are case-insensitive.
  - Full-line ; and # comments are supported.
  - Inline comments are not supported:

  DefaultGameSpeed = 5 ; invalid

  - If a key is repeated, the first declaration wins.
  - Single and double quotes are supported, but there is no escaped-quote parser.
  - Relative .. components are not rejected or canonicalised; modders should avoid them.
  - info.ini files larger than 1 MiB are ignored.

  ### Not owned by this DLL

  ParentMod appears in the binary because shared extension-root code is statically linked, but A2FOInfoIni does not
  consume or register it. Parent discovery belongs to the core.

  It also does not own:

  - [modules] activeX, requiredX, or rejectX
  - Any ODF commands
  - ART/RTS/GUI CFG fields
  - SPR, texture, SOD or localization conventions
  - Any save-format extension

  ### Verification

  - Current parser test passes.
  - Built and installed DLLs have different hashes, but differ in only eight PE metadata bytes—code and behaviour
    are effectively identical.

# A2FOInstantActionSettings.dll

  ### Activation

  Select the module using the ordinary module list:

  [modules]
  activeX = "A2FOInstantActionSettings"

  The activeX mechanism belongs to the core module loader, not this DLL.

  ### Automatic behaviour

  When enabled, it automatically:

  - Restores the Instant Action Load Settings button route.
  - Preserves the native host-only check.
  - Repairs missing Load-button bounds using the adjacent Save button and the fixed six-pixel gap.
  - Redirects an exact bare Settings.prf open to the resolved SettingsDirectory, when one is available.
  - Correctly decodes Fleet Ops’ native profile line:

  setupDetails = <1648 hexadecimal characters>

  - Guards against saved setups referring to a race absent from the current mod.
  - Replaces unreadable Instant Action toggle labels with a blank label instead of crashing.

  setupDetails is an existing Fleet Ops profile field representing an exact 824-byte structure. It is not a modder
  command and should not normally be edited manually.

  ### Fixed textual conventions

  - Profile filename: Settings.prf
  - Profile label: case-sensitive setupDetails
  - Button-caption fallback: English Load Settings

  The caption matcher ignores ASCII case, spaces, tabs, underscores and &, so these match:

  Load Settings
  &LOAD_SETTINGS
  loadsettings

  A translated caption will not match the WM_COMMAND fallback, although the coordinate-based mouse route may still
  work.

  ### Dependencies

  - Requires A2FOExtensions.dll and the supported Armada/Fleet Ops binaries.
  - A2FOInfoIni.dll is not a hard dependency.
  - However, profile-path redirection occurs only when the core can supply a resolved SettingsDirectory. Otherwise
    the native bare Settings.prf path remains.

  There are no:

  - ODF fields
  - info.ini fields
  - RTS_CFG.h, ART_CFG.h or GUI CFG settings
  - Localization keys
  - Sprite, texture or SOD conventions
  - New save/profile fields

  ### Findings

  1. The README says the corrected decoder runs only while reading the tracked Instant Action setup structure. The
     implementation is slightly broader: it intercepts any 824-byte blob read whose current text line begins with
     exact setupDetails. It does not actually require the tracked-load flag, matching destination or reader mode.
     Collision risk is low but the documentation overstates its isolation.

  2. The English Load Settings caption dependency is undocumented.
  3. The exact profile redirection requires the incoming path string to be precisely Settings.prf; alternate casing
     or .\Settings.prf is not redirected.

  4. The optional Advanced Settings diagnostics signature is part of mandatory preflight. If that diagnostic-only
     Fleet Ops function changes, the entire repair is disabled.

  The parser/geometry tests pass. Built and installed DLLs differ only in nine PE metadata bytes; executable
  behaviour is identical. Relevant source: A2FOHookExtensions/modules/A2FOInstantActionSettings/module.cpp:35,
  A2FOHookExtensions/modules/A2FOInstantActionSettings/setup_details_line.cpp:10, and A2FOHookExtensions/modules/
  A2FOInstantActionSettings/README.md:1.

  ## Technology-tree syntax

  List the actual weapon ODF in every applicable technology tree:

  fbphas.odf 0
  fbpulse.odf 1 fresear.odf
  fblockedweapon.odf -1
  fconditionallyblocked.odf -2

  Meanings are the normal Fleet Ops meanings:

  - 0: immediately available.
  - Positive number: that many following prerequisite projects must be available.
  - -1: impossible and prevents dependent projects.
  - -2: impossible itself, but does not automatically invalidate dependants.
  - Unlisted weapon: treated by this module as 0, so it remains available.

  For a weapon directly listed as -1 or -2, both forms prevent it firing. Their difference matters when other
  technology entries depend upon that project.

  ## Which ODF to list

  Use the weapon ODF assigned by the ship:

  weapon1 = "fbphas"

  fbphas.odf 1 fresear.odf

  Do not list:

  - The included parent such as phaser.odf.
  - The ship ODF carrying the weapon.

  ## Actual applicability

  The implementation is broader than the README wording suggests. It does not explicitly test for:

  cannon
  phaser
  pulse
  launcher
  torpedo

  Instead, it checks the native completed WeaponClass special flag:

  special = 0  // checked by A2FONormalWeaponTech
  special = 1  // bypasses this module

  Consequently, any WeaponClass reaching the shared Weapon::Trigger path with special = 0 is potentially governed by
  its .tt entry, even if it uses an unusual class label. special = 1 weapons remain under Fleet Operations’ native
  special-weapon technology handling.

  This behavior is visible in A2FOHookExtensions/modules/A2FONormalWeaponTech/module.cpp:118.

  ## Runtime behavior

  The decision occurs immediately before the native shot:

  target/range/obstruction checks
  → optional 3D fire-arc check
  → normal-weapon technology check
  → native Weapon::Trigger

  It therefore:

  - Prevents the shot itself.
  - Does not hide or remove the weapon.
  - Does not alter the weapon ODF or ordnance.
  - Applies to human and AI firing through the same trigger path.
  - Coexists with FireArcs, Turrets, and torpedo-ammunition prechecks.
  - Does not require A2FOTurrets.dll.

  The current owner’s team is resolved for every firing attempt. This means:

  - Newly completed research can enable an existing weapon.
  - Captured ships use the capturing team’s technology tree.
  - If the weapon is absent from the capturer’s tree, it defaults to available.
  - Every selectable .tt variant must contain the restriction; forgetting one silently leaves the weapon available.

  The shared gate is documented in A2FOHookExtensions/core/dllmain.cpp:2229.

  ## Failure and diagnostic behavior

  The module deliberately fails open when it cannot safely resolve:

  - The weapon or WeaponClass.
  - The project ID.
  - The weapon owner.
  - Team indices outside 0–63.
  - The team technology tree.
  - Required game signatures.

  A typo or missing weapon entry also effectively fails open because the weapon is considered unlisted.

  It logs only the first occurrence of each decision type per process:

  allowed (unlisted/default 0)
  allowed by listed entry
  blocked by listed entry

  The messages contain the numeric project ID and team index, not the ODF filename.

  CannonImp uses similar commands natively, but this DLL does not replace or extend CannonImp itself.

  ## ODF commands

  Put these in the weapon ODF—not its ordnance ODF:

  shotDelay0 = 0.1
  shotDelay1 = 0.1
  shotDelay2 = 2.0

  saveFireCyclePoint = 2
  shotCycleResetTime = 15.0

  This produces:

  first shot
  → wait shotDelay0 (0.1)
  → second shot
  → wait shotDelay1 (0.1)
  → third shot
  → wait shotDelay2 (2.0)
  → subsequent shots loop from index 2

  shotDelay0 controls the delay after the first successful firing attempt. It does not control initial weapon
  activation; native initial-delay behavior remains intact.

  Without saveFireCyclePoint, the default is 0, so the entire sequence repeats.

  ## Validation rules

  - Accepted numbered range: shotDelay0 through shotDelay63.
  - Entries must be contiguous from zero.
  - A gap invalidates the entire numbered policy:

  shotDelay0 = 0.1
  shotDelay2 = 1.0  // invalid because shotDelay1 is absent

  - Values must be finite and non-negative.
  - Zero is valid.
  - There is no practical upper limit beyond finite floating-point range.
  - saveFireCyclePoint must be a whole, non-negative index inside the effective sequence.
  - shotCycleResetTime must be finite and non-negative.
  - A malformed numbered policy falls back to ordinary shotDelay.

  Numeric strings are also accepted:

  shotDelay0 = "0.1"
  shotDelay1 = "0.25f"

  Expressions and trailing text are not accepted.

  One undocumented edge case: shotDelay64 is explicitly detected and rejects the policy, but shotDelay65 and above
  are never queried and are silently ignored.

  The parser is in A2FOHookExtensions/modules/A2FOPointDefenseCycles/module.cpp:188, with the pure sequence logic in
  A2FOHookExtensions/modules/A2FOPointDefenseCycles/firing_cycle.cpp:23.

  ## Unnumbered shotDelay

  For either supported point-defense class:

  shotDelay = 3.5

  is treated as a one-entry sequence when no numbered policy exists.

  For PointDefenseLaser, the intended runtime replaces Roots’ late timer check with a proper pre-fire gate. This
  prevents target/ordnance searches while the timer remains positive.

  For OrdnanceDefenseWeapon, its existing successful-shot timer assignment is replaced with the selected cycle
  delay.

  ## Idle reset

  shotCycleResetTime = 15.0

  The idle countdown starts only after the active firing delay reaches zero. If the weapon remains ready but finds
  nothing to intercept for 15 seconds, the next shot uses shotDelay0.

  Zero or omission disables reset.

  For toggleable PointDefenseLaser weapons, the implementation only advances the timer while the native simulation
  considers the weapon active. Turning it off therefore pauses the timer and idle-reset processing rather than
  instantly resetting the cycle.

  ## Runtime state

  State is stored per Weapon instance:

  - Current next-delay index.
  - Remaining idle-reset time.
  - Internal firing counter.

  Therefore:

  - Multiple ships using the same WeaponClass have independent cycles.
  - Multiple weapon instances on one ship remain independent.
  - Capturing a ship preserves its current cycle.
  - State is removed when the Weapon is destroyed.

  Internal save fields:

  a2fo_pointDefenseCycleIndex
  a2fo_pointDefenseCycleIdle

  These are save-stream labels, not ODF commands.

  Configured numbered-cycle saves require those extra fields. Saves made before enabling a cycle will fail the
  module’s configured Weapon load because the fields are absent; similarly, removing the module from a save
  containing its extra state should be treated as unsafe. Scalar-only shotDelay weapons do not receive this sidecar
  save block.

# A2FORGBTextures.dll

  ## Supported asset layout

  Any loose extension root can provide:

  Textures/RGB/
  Textures/Index8/
  Textures/Compressed/

  Folder and filename matching is case-insensitive, so the current lowercase Textures/rgb works.

  Typical material flow:

  SOD material: mytexture
  Fleet Ops tries: Textures/mytexture.dds
  Then fallback:  Textures/mytexture.tga
  A2FORGBTextures redirects that TGA request to the winning legacy folder

  Subdirectories are scanned recursively to depth 32. Reparse points are ignored, maps are built once during
  initialization, and newly added files require restarting the game.

  ## Precedence

  Across extension roots, later/more-specific roots win:

  shared Data → parent mods → active child mod

  Inside one root, a completed root-level TGA fallback uses:

  Textures/name.tga
  Textures/RGB/name.tga
  Textures/Index8/name.tga
  Textures/Compressed/name.tga

  The first line has highest same-root priority. A child’s Index8 or Compressed file still overrides a parent’s RGB
  file because root precedence is evaluated first.

  Important distinctions:

  - Native or packaged DDS/TGA resolution gets its normal attempt before legacy fallback.
  - Explicit Textures\RGB\..., Textures\Index8\..., and Textures\Compressed\... requests stay inside that namespace.
  - Only TGAs are flattened into the root-level fallback.
  - A DDS inside Textures/RGB is not a replacement for Textures/name.dds unless the request explicitly contains RGB.
  - Legacy folders must be loose directories; archived-only folders cannot activate the scanner.

  The selection logic is visible in A2FOHookExtensions/modules/A2FORGBTextures/module.cpp:937.

  ## TGA formats

  Already-safe files are passed directly when their header declares:

  - Uncompressed true-colour type 2
  - 24-bit or 32-bit pixels
  - Nonzero dimensions
  - No colour map

  The module can convert these to temporary uncompressed 24/32-bit type-2 TGAs:

  - Colour-mapped types 1 and 9
  - True-colour types 2 and 10, including 16-bit
  - Grayscale types 3 and 11
  - RLE types 9, 10, and 11
  - 8/16-bit palette indices
  - 15/16/24/32-bit palettes

  Limits are 128 MiB input and 256 MiB prepared output. Converted files are cached in a process-specific temporary
  directory and removed during normal shutdown.

  Explicit Index8 and Compressed requests retain their original bytes for their corresponding native loader.
  Conversion happens when those files are flattened through Fleet Operations’ true-colour root-TGA fallback.

  ### Important behavioral details

    boundary is 116.34 + 5.73 + 0.50 = 122.57; radius 150 therefore reaches approximately 272.57 units from the

    restart the match/game.

    there are no animation-speed or phase-offset commands.

  ## Runtime behavior

  Each mounted turret is a complete native object:

  - Own SOD, weapons, shields/hitpoints, team, race and target selection.
  - Added to the current mission object table.
  - Anchored to the parent after every simulation tick.
  - Whole SOD rotates rigidly; separate yaw base/barrel articulation is unsupported.

    configured rest position.

  ## Damage modifiers

  shieldDamageModifier = 2.0
  hullDamageModifier = 0.5

  With resolved base damage D:

  - A shielded hit inflicts D × 2.0 against shields.
  - An exposed-hull hit inflicts D × 0.5.
  - If the doubled hit breaks shields, the native spillover is corrected to the 0.5 hull scale.
  - Native system/hull distribution operates on the corrected hull amount.

  The modifiers are applied after Armada has resolved the weapon’s ordinary per-hit damage. They do not change:

  - hitChance
  - Range or firing rate
  - Ordnance speed/lifetime
  - Fire arcs or technology checks
  - Weapon sprites and sounds
  - Special-weapon side effects

  Both booleans suppress primary damage only. An ordnance may still impact, display effects, or perform its own
  special behavior.

  ### Valid values

  - Finite values from 0 upward are accepted.
  - 0 removes damage from that channel.
  - Negative, NaN, or infinite entries are replaced with 1.0.
  - There is no upper cap; extreme values risk overflowing the final damage calculation.
  - Booleans use Armada’s native boolean parser.

  ## Target-specific damage tables

  Both modifiers accept native cLookup target tables:

  shieldDamageModifier =
      1.0
      "fed_sovereign.odf" 0.5
      "bcruise1.odf" 2.0

  hullDamageModifier =
      1.0
      "fed_sovereign.odf" 1.5
      "bcruise1.odf" 0.25

  Rules:

  - The first number is the fallback.
  - Each quoted target ODF is followed by its multiplier.
  - Matching uses Armada’s native project-ID mechanism.
  - The target’s actual object-class ODF is used.
  - Capture or team/race changes do not change its class lookup.
  - Upgraded/replacement classes with different ODFs need their own entries.
  - The booleans are not target tables; only the two modifiers support overrides.
  - A child weapon inherits its parent’s complete lookup when it does not redeclare that modifier.
  - Invalid target values are individually replaced with 1.0.

  A zero target-specific hull multiplier is the closest equivalent to making one target immune to that weapon’s
  ordinary hull damage.

  ## Shield-breaking calculation

  For a normal weapon with:

  shieldDamageModifier = S
  hullDamageModifier = H

  the DLL initially scales a shielded hit by S. Once Armada calculates shield absorption and spillover, it scales
  only the resulting hull/system amount by:

  H / S

  The net spillover therefore has the intended H multiplier rather than inheriting the shield multiplier.

  If S = 0, the shield loses nothing and no spillover can be generated.

  ## Native ignoreShield interaction

  The module only adds DamageInfo flags; it never clears existing ordnance flags such as native ignoreShield or
  shield-only damage.

  For an ordinary ignoreShield weapon:

  - Leave canDamageShields = true; the native bypass flag remains present.
  - With nonzero modifiers, the spillover correction normally produces the configured hull multiplier.
  - Setting canDamageShields = false while shields remain blocks the complete hit, overriding the practical bypass
    behavior.

  ### Identified zero-modifier edge case

  This combination is problematic:

  // General weapon ODF
  shieldDamageModifier = 0
  hullDamageModifier = 1

  // Its ordnance already has:
  ignoreShield = 1

  While the target has positive shields, the DLL classifies the hit as shielded and first multiplies it by zero.
  Because division by the zero shield modifier is deliberately suppressed, it cannot recover the intended hull
  multiplier. The supposedly shield-bypassing hit consequently inflicts zero hull damage.

  Avoid shieldDamageModifier = 0 on weapons whose ordnance uses ignoreShield; use channel booleans or a small
  nonzero shield multiplier according to the intended behavior.

  ## DirectionalShields integration

  The live bridge sequence is:

  DirectionalShields loads
    → waits for shared Craft::Damage owner
  WeaponDamageControls loads
    → installs Craft::Damage
    → DirectionalShields connects

  This succeeded in the current log.

  Before WeaponDamageControls selects the shield or hull modifier, DirectionalShields temporarily presents the
  struck facing’s current value. Therefore:

  - A hit against a charged facing uses the shield modifier.
  - A hit against a depleted facing uses the hull modifier.
  - Other charged facings do not prevent exposed-facing hull damage.
  - Spillover correction applies to the struck facing’s shield break.

  Active directional policies exist for fbattle.odf and fbase.odf, although no currently loaded weapon uses a
  WeaponDamageControls policy.

  ## Craft ODF commands

  Add these to a Craft-derived ship or station:

  wreckage = "mwreck"
  wreckageChance = 75

  Rules:

  - wreckage is the replacement GameObjectClass ODF basename.
  - wreckageChance accepts 0..100, including fractional percentages.
  - Missing wreckageChance defaults to 100.
  - 0 reliably disables replacement.
  - 100 always creates it.
  - Values below zero, above 100, NaN, infinity or malformed text are rejected rather than clamped.
  - Empty or missing wreckage leaves native destruction unchanged.
  - Outer whitespace is trimmed.
  - Replacement names are limited to 255 characters.
  - Validated characters are ASCII letters, numbers, _, -, and ..
  - Paths and spaces are rejected. Use a simple basename such as mwreck.
  - Normal ODF inheritance applies.

  An inherited policy can be disabled in a child with either:

  wreckage = ""

  or:

  wreckageChance = 0

  A wreckageChance without a valid wreckage has no useful effect.

  ## Runtime sequence

  The actual destruction flow is:

  Craft enters Craft::Explode
    → core snapshots ODF, handle, team and transform
    → native Craft::Explode completes
    → A2FOWreckage performs its deterministic chance roll
    → core finds and constructs the replacement class
    → replacement is added to the current AI mission

  This means the DLL does not suppress or replace the source’s native explosion, debris, sound or fireball. It adds
  a fresh object after native destruction finishes.

  Only the checked Craft::Explode path is covered. Ordinary non-Craft GameObjects do not generate this event.

  ## What the replacement inherits

  The module always requests:

  - Position
  - Rotation

  It always assigns:

  - Neutral ownership/team 0

  It does not inherit:

  - Original owner or team
  - Race state
  - Hull, shields or subsystem damage
  - Velocity or angular momentum
  - Orders or target
  - Crew
  - Experience/rank
  - Cargo or resources
  - Object label/name
  - Source ScaleSOD
  - Source animation state

  The replacement is a newly constructed native object using its own ODF defaults. A moving ship’s wreck therefore
  does not automatically continue drifting or spinning.

  The underlying core API supports original ownership, but A2FOWreckage.dll hardcodes neutral ownership and provides
  no ODF command to change it.

  ## Chance determinism

  The chance seed is derived from:

  - Normalized source ODF basename
  - Source object handle
  - Source team
  - Complete death transform

  The seed is then mixed independently rather than consuming Armada’s global random stream. This avoids perturbing
  unrelated gameplay randomness and should give synchronized peers the same decision when their object state
  matches.

  The same destroyed object state always produces the same result. Different handles, teams or death positions
  normally produce different rolls.

  - ScaleSOD = 1.4

  - No replacement ScaleSOD

  smaller than the destroyed Sovereign. Give a custom wreckage ODF its own ScaleSOD or use a ship-specific wreck SOD
  if matching size matters.

  ## Replacement-class possibilities

  Although the command is named wreckage, the core can construct any valid native GameObjectClass ODF. It could
  therefore create:

  - Static background wreckage
  - A neutral derelict Craft
  - A resource object
  - A hazard
  - Another scripted or weapon-equipped object

  All ordinary behavior must be authored in that replacement ODF. A2FOWreckage itself supplies no salvage, capture,
  lifetime, resource-transfer or drifting mechanics.

  Be careful with Craft replacement chains. If a replacement Craft has its own wreckage policy, destroying it can
  create another replacement. Self-referential policies could produce an indefinite sequence of objects across
  repeated destructions.
